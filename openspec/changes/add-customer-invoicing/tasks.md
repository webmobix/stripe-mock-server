## 3. Invoice creation and reading

- [x] 3.2 Implement `create_invoice` (`POST /v1/invoices`) in `src/api/v1.rs`: require `customer` (reject with `invalid_request_error` when absent, `not_found` when unknown for the account), require at least one line, resolve each `lines[][price]` through the account's prices (reject with `invalid_request_error` for an unknown price), default `quantity` to 1, and reject a line whose price currency differs from the first line's. - [x] 3.4 Copy the customer's tax ids to the invoice's `customer_tax_ids` when creating the invoice. Verify with an integration test that a customer created with an `eu_vat` tax id yields an invoice whose `customer_tax_ids` contains that type and value.

Verify with an integration test that listing with `customer=...` returns only that customer's invoices and that the lines endpoint returns a list envelope holding the invoice's lines.
- [x] 3.6 Emit `invoice.created` from `create_invoice` using the existing transaction-then-`dispatch_event` pattern. Verify with an integration test that an `invoice.created` event is received whose `data.object.id` is the new invoice.

## 4. Invoice lifecycle

- [x] 4.1 Implement a single status-transition table in `src/api/v1.rs` covering `draft → open` (finalize), `open → paid` (pay), `draft|open → void` (void), and `open → uncollectible` (mark uncollectible), and a helper that rejects any other transition with an `invalid_request_error` leaving the invoice unchanged. Verify with unit tests on the transition helper that each allowed and rejected pair behaves as specified.
- [x] 4.2 Implement `finalize_invoice` (`POST /v1/invoices/{id}/finalize`): move a draft invoice to `open`, set `finalized_at`, set `amount_due` to the invoice `total`, and emit `invoice.finalized`. Verify with an integration test that finalizing sets `status` to `open`, `amount_due` equal to `total`, and that finalizing an already-open invoice is rejected and leaves the status unchanged.
- [x] 4.3 Implement `void_invoice` (`POST /v1/invoices/{id}/void`) and `mark_invoice_uncollectible` (`POST /v1/invoices/{id}/mark_uncollectible`), setting `voided_at` for the void path, and emit `invoice.voided` and `invoice.marked_uncollectible`. Verify with an integration test that voiding an open invoice sets `status` to `void`, that marking it uncollectible sets `status` to `uncollectible`, and that marking a paid invoice uncollectible is rejected.
- [x] 4.4 Register the finalize, void, and mark-uncollectible routes in `src/lib.rs`. Verify with an integration test that the three endpoints reach their handlers and that an unknown invoice id returns `not_found`.

## 5. Payment intents

- [x] 5.1 Extend `PaymentIntentRow` in `src/models.rs` with the `invoice` column and render it on the payment intent object in `to_json()`, alongside `id`, `object`, `amount`, `currency`, `customer`, `status`, `created`, `metadata`, and `livemode`. Verify with a unit test that a payment intent with an invoice renders that invoice id.
- [x] 5.2 Implement `create_payment_intent` (`POST /v1/payment_intents`) in `src/api/v1.rs`: require `amount` (reject with `invalid_request_error` when absent), default `currency` to `usd`, accept an optional `customer` and `invoice` (reject with `not_found` for an unknown invoice for the account), store `status` as `requires_payment_method`, and emit `payment_intent.created`. Verify with an integration test that creating a payment intent returns a `pi_` id with the stored amount and currency, that omitting the amount is rejected, and that an unknown invoice is rejected with no payment intent created.
- [x] 5.3 Implement `get_payment_intent` (`GET /v1/payment_intents/{id}`) and `list_payment_intents` (`GET /v1/payment_intents`, list envelope, `customer` and `invoice` filters) in `src/api/v1.rs`, and register the routes together with the create route in `src/lib.rs`. Verify with an integration test that listing with `invoice=...` returns only that invoice's payment intents.
- [x] 5.4 Implement the settlement rule in one place in `src/api/v1.rs`: on a `succeeded` resolution of a payment intent that references an invoice, add its `amount` to the invoice `amount_paid`, recompute `amount_remaining` (never below zero), and when `amount_paid` reaches `amount_due` set the invoice `status` to `paid` with `paid_at` set; emit `invoice.payment_succeeded` and, on full coverage, `invoice.paid`. Verify with integration tests that a full payment sets the invoice to `paid` with `amount_remaining` 0 and emits both events, and that a partial payment increases `amount_paid`, decreases `amount_remaining`, and leaves the invoice `open`.
- [x] 5.5 Implement `POST /internal/payment_intents/{id}/resolve` in `src/internal.rs`: accept `status` of `succeeded`, `failed`, or `canceled`, reject any other value with an `invalid_request_error`, return `not_found` for an unknown id, set the payment intent status, emit `payment_intent.succeeded`, `payment_intent.payment_failed`, or `payment_intent.canceled`, and apply the settlement rule from 5.4 (a `failed` resolution leaves the invoice amounts and status unchanged and emits `invoice.payment_failed`). Register the route in `src/lib.rs` and rely on the existing `/internal` cross-origin guard. Verify with integration tests that resolving with each of the three statuses sets the status and emits the matching event, that an unsupported status is rejected, and that a failed resolution leaves the invoice unchanged.
